# 代码审查维度清单

审查的完整性靠**固定维度矩阵**保证，不靠临场发挥。
用它做两件事：① 开工前决定要审哪些；② 交付前检查有没有维度被漏掉。

## 一条硬规则

> **每条发现都必须落到三选一，否则该维度视为"未审查完成"：**
> ① 自动化（脚本 / lint / 测试 / CI）
> ② 人工清单项（写进 checklists，每次照做）
> ③ 明确"不适用"并写理由

只写进问题清单、没有去向的发现，等于没发现——这是上一次官网复盘的直接教训。

## 12 个维度

| # | 维度 | 必须查什么 | 证据形式 | 自动兜底 |
|---|---|---|---|---|
| 1 | 依赖与包管理 | 锁文件唯一、`packageManager`/`engines`、同类库唯一、import 与声明一致、许可证、体积、安全审计 | `npm ls --depth=0`、锁文件列表、import 清单 | `check-deps.mjs` |
| 2 | 架构与分层 | 路由/组件/数据/工具边界；页面是否反向 import 组件私有样式 | 目录树 + import 关系 | 人工清单 |
| 3 | 状态与副作用 | 全局监听、滚动锁、inert、定时器是否成对清理；是否有多套实现 | grep `addEventListener` / `overflow` | 人工清单 |
| 4 | 组件契约 | props 是否封闭；是否靠类名/id/`querySelector` 跨组件通信 | 组件源码 + DOM 查询统计 | 人工清单 |
| 5 | 样式体系 | token 覆盖、分层、断点数量、`!important`、裸 z-index、全局类污染 | `stylelint` 报告 | `stylelint` |
| 6 | 数据与事实 | 单一来源、派生字段、字段一致性、占位数据是否可能上线 | 数据文件 + 引用点 | `check-facts.mjs` + 测试 |
| 7 | 性能 | LCP/CLS/TBT 候选、资源体积、字体加载、bundle 体积、滚动热路径 | Lighthouse、体积报告 | `check-assets.mjs` |
| 8 | 可访问性 | landmark、heading 层级、焦点可见、对比度、键盘路径、reduced-motion | axe/Lighthouse + 人工键盘走查 | 人工清单 |
| 9 | SEO / GEO | title/description/canonical/OG、robots、sitemap、Schema、SSR 可见性 | `curl` 抓 HTML + Schema 校验 | 测试 + 人工清单 |
| 10 | 构建与部署 | 构建产物、环境变量、缓存策略、回滚方式、域名/HTTPS | `next build` 输出 + 部署检查 | CI |
| 11 | 质量护栏 | lint/test/typecheck 是否真的能跑；CI 是否阻塞合并 | 实际跑一遍 | CI |
| 12 | 交付与合规 | 许可证、备案、隐私说明、占位符、git 卫生、素材授权 | 清单核对 | `check-facts`（占位符） |

## 每个维度的最低证据（不能只写"已检查"）

- **依赖**：锁文件数量、`package.json` 依赖清单、同类库列表
- **样式**：`stylelint` 输出、token 数量 vs 字面量数量、`@media` 与断点统计
- **可访问性**：对比度实算值、键盘走查路径、截图
- **SEO**：抓取到的 HTML 片段、Schema JSON、canonical/OG 实际值
- **性能**：Lighthouse 分数与 LCP/CLS 元素、资源体积清单

## 合成阶段的三个必做

1. **按"改动成本 × 影响面"排序**，单独输出 Top 5 可立即执行项；
2. **每类问题至少产出一条"下次规则"**，并标明由什么兜住；
3. **复述检查**：另一个人只看结论，能否指出证据在哪个文件哪一行。做不到就说明结论太虚。

## 已发生的漏项（作为反例保留）

**依赖维度曾整类缺失。** 上一次官网审查报告里其实写了"两套动画库 gsap + framer-motion""双 lock 文件"，但：

- 没有独立维度，被塞进"工程化"的一句话；
- 没有进入 Top 5 行动项；
- 没有对应规则和检查。

结果：用户自己发现了问题，才补上 `check-deps.mjs`。
**教训：发现 ≠ 结论；没有去向的发现会在合成阶段蒸发。**
